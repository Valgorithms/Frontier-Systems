# Paid doorway opening topology v1 (internal)

`ProductionSimulationSystem.construction_openings(context, expected_revision)` is a synchronous read-only server interface. It accepts the authenticated context and a bounded integral current Production revision (integral JSON numbers accepted; booleans, strings, fractions, nonfinite and stale values rejected). It has no network message, player command, persisted record or external serialization schema.

The existing Inventory production visibility capability must resolve a current bound body before any geometry is returned. Include every canonical region wall, only the current principal's paid horizontal panels, and only that principal's paid doors attached to the currently bound body. Legacy walls have no ownership metadata: their inclusion asserts no ownership and grants no mutation rights. Excluded foreign doors/panels cannot complete a layout. The single rectangular layout restriction applies to the complete included set; unrelated region walls can make it unsupported. No caller-supplied IDs or geometry are accepted by the owner query.

The detached `ConstructedDoorOpeningTopology.assess` input has exactly schema_version=1, production_revision, revision-matched v1 walls, at most 64 strict surfaces and at most 16 openings. Each opening contains only door_id, position (integer millimetres), quarter_turn (0 or 1). Canonical paid poses use the 50 mm grid at y=0. IDs are unique across walls/openings. Descriptors cannot confer construction identity or rights. Production derives fresh inputs on every call, including after same-revision restore; no cached assessment survives a restore.

The algorithm keeps solid-wall and aperture intervals separate. All pieces must lie on one of the four exact 100 mm rectangular wall bands, with no positive-area overlap. Each side's disjoint wall/aperture interval union must cover it exactly; apertures cannot replace corner joins. Missing pieces, unsupported layouts and floor/ceiling gaps produce open_or_unsupported; malformed descriptors, overlaps and revision mismatch reject. Apertures never enter existing solid-wall closure assessment.

A doorway's installation frame is 1000 x 2000 x 100 mm. Its actual clear opening is 900 x 1900 mm, with a 900 x 1900 x 50 mm leaf. These are geometry descriptions, not pressure flow areas or seal ratings. Neither open nor closed manual leaves seal: Access still requires zero seal condition and pressure area. Pressure volumes, gas, stock, Access state and movement are untouched.

Floor and ceiling coverage uses the intersection of each validated non-overlapping paid surface with the interior rectangle. Support panels outside the rectangle are permitted; this matters because a door's paid swing-support footprint extends beyond the inner wall face. The complete interior must be covered at y=0 and y=2000. Existing construction_closure keeps its previous stricter surface semantics unchanged.

A successful result contains only schema_version=1, production_revision, status, interior_bounds_millimetres and sorted door_ids. Status is enclosure_with_unsealed_openings only when a rectangular aperture complement and both surfaces are complete; otherwise open_or_unsupported. Bounds are empty when no rectangular complement exists. Door IDs identify only included apertures in a recognized rectangular complement, including when surfaces remain missing; unsupported complements return none. Results are detached and deterministic. There is no room ID, sealed flag, material data, foreign identity, pressure grant, flow area or persisted topology owner. The legacy closure query still reports open_or_unsupported for the doorway with either leaf position.

This code runs on demand without a tick cadence, events, counters or asynchronous effects. Existing Production revision/tick/counters remain authoritative. No new dependencies, settings or assets are introduced. First-party code and documentation are MIT.

The owner integration positive uses a bounded explicitly seeded test fixture, not an ore-to-room gameplay claim. Default iron ore yields 6 kg refined iron; The 7.6 kg example enclosure plus 2 kg fabricated crowbar cannot currently be built from that default bootstrap. See the milestone document for exact test input, accounting and the deferred finite resource prerequisite.
